# Datacendia Platform Security & Code Audit — April 13, 2026

## Scope
Full security, code quality, and infrastructure audit of **datacendia-core** (Community Edition).

---

## Executive Summary

This audit identified **6 CRITICAL**, **10 HIGH**, **14 MEDIUM**, and **8 LOW** severity findings across security, code quality, and infrastructure. The most urgent issues are **unauthenticated access to environment secrets**, a **debug endpoint exposing SMTP credentials**, **private keys logged to stdout**, **Vault running in dev mode in production config**, and **SQL injection vectors in the vector search service**.

## CRITICAL Findings

### C1. Unauthenticated Environment Config API — Full Secret Exposure
**File:** `backend/src/routes/env-config.ts`
**Mounted at:** `backend/src/routes/domains/platform.domain.ts:52`

The `/api/v1/admin/env-config` endpoint allows **reading and writing the `.env` file** (DATABASE_URL, JWT_SECRET, REDIS_PASSWORD, STRIPE_SECRET_KEY, all API keys) with **zero authentication**. No `authenticate`, `devAuth`, or `requireRole` middleware is applied at either the route or domain router level.

**Impact:** Any unauthenticated user can exfiltrate all platform secrets and modify configuration to gain full system access.

**Fix:** Add `authenticate` and `requireRole('SUPER_ADMIN')` middleware to the env-config router. Consider removing this endpoint entirely — runtime `.env` editing is an anti-pattern.

---

### C2. Debug SMTP Endpoint Exposed Without Auth or Environment Guard
**File:** `backend/src/index.ts:166-191`

```typescript
app.get('/debug/smtp', async (_req, res) => {
  // Exposes SMTP host, port, user, whether password is set, from address, sales email
```

This endpoint is mounted **before all middleware** (including auth) and has **no environment guard** (`NODE_ENV === 'development'`). It exposes SMTP configuration details in production.

**Impact:** Information disclosure enabling targeted attacks against email infrastructure.

**Fix:** Remove this endpoint entirely, or wrap it in `if (config.nodeEnv === 'development')`.

### C3. Private Keys and Master Seed Logged to Stdout
**File:** `backend/src/services/crypto/KeyManagementService.ts:112-118`

```typescript
logger.warn(`   CENDIA_ED25519_PRIVATE_KEY=${bytesToHex(this.ed25519Keys.privateKey)}`);
logger.warn(`   CENDIA_DILITHIUM_PRIVATE_KEY=${bytesToHex(this.dilithiumKeys.privateKey)}`);
logger.warn(`   CENDIA_MASTER_SEED=${masterSeed}`);
```

On first boot (when env vars aren't set), the KMS service logs **full private keys and the master seed** in plaintext to stdout/logs. In containerized deployments, these logs are typically shipped to centralized logging (CloudWatch, Datadog, etc.).

**Impact:** Complete compromise of the cryptographic signing infrastructure. Anyone with log access can forge evidence packages, decision packets, and audit seals.

**Fix:** Never log private key material. Instead, write keys to a secure file with restricted permissions, or require manual key provisioning.

### C4. Multiple Sensitive Routes Completely Unprotected
**Files:** Multiple route files under `backend/src/routes/`

The following sensitive endpoints have **zero authentication**:

| Route | File | Risk |
|-------|------|------|
| `/api/v1/admin/env-config` | `env-config.ts` | Read/write all secrets |
| `/api/v1/settings/*` | `settings.ts` | Org settings, API keys, billing, user management |
| `/api/v1/command/execute` | `command.ts` | AI command execution |
| `/api/v1/auto-heal/*` | `auto-heal.ts` | AI-powered code fix generation |
| `/api/v1/schema/*` | `schema.ts` | Database schema mapping |
| `/api/v1/marketing-studio/*` | `marketing-studio.ts` | AI content generation |
| `/api/v1/platform-assistant/*` | `platform-assistant.ts` | AI platform assistant |

Additionally, `settings.ts` uses an **unvalidated `x-tenant-id` header** for tenant isolation — any client can impersonate any tenant.

**Only 1 of 14 domain routers (`data.domain.ts`) applies authentication at the domain level.** The other 13 rely entirely on individual route files to implement their own auth, and many don't.

**Fix:** Apply `devAuth` (or `authenticate` in production) at the domain router level for all domains. Add `requireRole` to admin routes.

### C5. SQL Injection Vectors in VectorService
**File:** `backend/src/services/storage/VectorService.ts`
**Lines:** 176, 179, 189, 261, 264, 274, 350, 366

```typescript
// vectorString is interpolated directly into SQL, not parameterized
const vectorString = `[${queryEmbedding.join(',')}]`;
let sql = `SELECT ... 1 - (embedding <=> '${vectorString}'::vector) as similarity ...`;
const results = await this.prisma.$queryRawUnsafe<any[]>(sql, ...params);
```

The `vectorString` is string-interpolated into raw SQL across 8+ locations. While the vector currently comes from `generateEmbedding()` (which should return numbers), this is a dangerous pattern — if the embedding service is compromised or returns unexpected data, it enables SQL injection.

Additionally, `AdapterManager.rawQuery()` at `backend/src/adapters/AdapterManager.ts:62` exposes `$queryRawUnsafe` as a public method.

**Fix:** Pass vector strings as parameterized values (Prisma tagged template literals) or validate that the embedding array contains only finite numbers before interpolation.

---

### C6. Vault Running in Dev Mode in Production Docker Compose
**File:** `docker-compose.production.yml`

The production Docker Compose configures HashiCorp Vault with `VAULT_DEV_ROOT_TOKEN_ID`, which means Vault runs in **development mode** — all secrets stored in-memory (lost on restart), no authentication backend, no audit logging, and a predictable root token.

**Impact:** All secrets managed by Vault are ephemeral and accessible without authentication. Complete compromise of secrets management.

**Fix:** Configure Vault in server mode with proper storage backend (Consul, Raft), authentication (AppRole, Kubernetes auth), and TLS.

## HIGH Findings

### H1. Hardcoded Default Passwords in Docker Compose and Config
**Files:**
- `docker-compose.yml:9` — `datacendia_secure_2024`
- `docker-compose.yml:27` — `datacendia_redis_2024`
- `docker-compose.yml:44` — `datacendia_graph_2024`
- `docker-compose.yml:132` — `your-super-secret-jwt-key-change-in-production`
- `backend/src/config/index.ts:94` — `datacendia_redis_2024` hardcoded as default

These defaults make it trivial to gain access if the `.env` file isn't properly configured. The Redis password default is also hardcoded in the application config, not just docker-compose.

**Fix:** Remove all default passwords. Fail startup if required credentials are not explicitly provided in production.

---

### H2. JWT Refresh Secret Derived from Access Secret
**File:** `backend/src/config/index.ts:121,140`

```typescript
jwtRefreshSecret: process.env.JWT_REFRESH_SECRET || (process.env.JWT_SECRET ? process.env.JWT_SECRET + '-refresh' : undefined),
```

If `JWT_REFRESH_SECRET` is not set, the refresh secret is `JWT_SECRET + '-refresh'`. Anyone who knows the access token secret can trivially derive the refresh token secret.

**Fix:** Require `JWT_REFRESH_SECRET` as a separate, independently generated secret. Fail startup if not provided in production.

---

### H3. CSP Allows `unsafe-inline` for Scripts
**File:** `backend/src/index.ts:220`

```typescript
scriptSrc: ["'self'", "'unsafe-inline'"],
```

Allowing `unsafe-inline` for scripts defeats most XSS protections that CSP provides.

**Fix:** Remove `'unsafe-inline'` from `scriptSrc`. Use nonces or hashes for inline scripts if needed.

---

### H4. CORS Origin Matching Uses Substring Check
**File:** `backend/src/index.ts:237-244`

```typescript
if (origin.includes('localhost') || origin.includes('127.0.0.1')) {
  return callback(null, true);  // In development
}
if (origin.includes('railway.app') || origin.includes('datacendia')) {
  return callback(null, true);  // In all environments
}
```

The substring check means `evil-datacendia.com` or `railway.app.attacker.com` would be allowed. The railway.app/datacendia check applies in **all environments**, not just development.

**Fix:** Use exact origin matching or proper domain suffix validation (e.g., `.endsWith('.railway.app')`).

---

### H5. CSRF Protection Only Enforced in Production
**File:** `backend/src/index.ts:318-320`

```typescript
if (config.nodeEnv === 'production') {
  app.use('/api/', csrfProtection);
}
```

CSRF protection is completely disabled in development and test environments. Combined with the dev auth bypass, this allows unauthenticated state-changing requests.

**Fix:** Enable CSRF in all environments, with a dev opt-out via explicit env var only.

### H6. `dangerouslySetInnerHTML` Without Sanitization
**Files:**
- `src/components/crypto/CendiaStampSeal.tsx:84` — renders SVG content
- `src/pages/cortex/ops/OpsAgentsPage.tsx:358` — renders HTML content

Both instances render content via `dangerouslySetInnerHTML` without visible DOMPurify or other sanitization.

**Fix:** Sanitize all HTML/SVG content with DOMPurify before rendering via `dangerouslySetInnerHTML`.

### H7. 322 Backend TypeScript Errors (Unchanged Since April 6 Audit)
**File:** `backend/tsconfig.json`

The backend still has 322 TypeScript errors (131 implicit `any`, 82 missing properties, 46 type-as-value errors). This was flagged as critical in the April 6 audit and remains unfixed.

**Impact:** Undermines type safety across the entire backend. Type errors can mask real bugs and security vulnerabilities.

**Fix:** Prioritize fixing TS7006 (implicit any) errors first, then TS2693 (Prisma type-vs-value).

### H8. CI Pipeline Continues on Type Check and Lint Failures
**File:** `.github/workflows/ci.yml:43-44,47-48,118-119,123-124`

```yaml
- name: Type check
  run: npx tsc --noEmit --skipLibCheck
  continue-on-error: true    # <-- Type errors don't fail CI

- name: Lint
  run: npm run lint
  continue-on-error: true    # <-- Lint errors don't fail CI
```

Both frontend and backend type checks and linting are set to `continue-on-error: true`, meaning the CI pipeline passes even with type errors and lint violations.

**Fix:** Remove `continue-on-error: true` from type check and lint steps. Fix blocking errors first.

### H9. `prisma db push --accept-data-loss` in Production Entrypoints
**Files:**
- `backend/docker-entrypoint.sh:11`
- `backend/docker-entrypoint.railway.sh:51`

Both entrypoint scripts fall back to `prisma db push --accept-data-loss` if migrations fail. This can silently drop columns and tables in production.

**Fix:** Use `prisma migrate deploy` exclusively in production. If migrations fail, halt startup and alert — don't fall back to destructive operations.

### H10. TruffleHog Secret Scanner Uses Unpinned `@main`
**File:** `.github/workflows/security.yml`

TruffleHog is pinned to `@main` instead of a specific version, meaning a supply chain attack on the TruffleHog repo could inject malicious code into your CI pipeline.

**Fix:** Pin to a specific commit SHA or release tag.

## Additional Security Findings (from deep scan)

### S1. API Keys Stored in Browser localStorage — HIGH
**File:** `src/lib/laws/openstates.ts:227,239`

The OpenStates API key is stored in `localStorage`, which is vulnerable to XSS. Any successful XSS exploit can steal this key.

**Fix:** Move API key storage to the backend. Access OpenStates via a backend proxy endpoint.

### S2. JWT Tokens in localStorage — HIGH (Known/Documented)
**File:** `src/lib/api/client.ts`

Access and refresh tokens are stored in `localStorage`. This is documented in `SECURITY.md` as a known tradeoff with httpOnly cookies as a future improvement.

**Fix:** Implement httpOnly, Secure, SameSite=Strict cookies for token storage.

### S3. File Upload Missing MIME Type Validation — MEDIUM
**File:** `backend/src/routes/upload.ts`

File upload validation only checks file extension, not MIME type or magic bytes. Malicious files can bypass by simply renaming.

**Fix:** Validate `file.mimetype` and file magic bytes in addition to extension. Ensure ClamAV scanning is applied to all uploads.

### S4. CSP Also Allows `unsafe-eval` in Security Module — MEDIUM
**File:** `backend/src/security/index.ts:114-126`

In addition to `unsafe-inline` (H3), the security module's CSP also includes `unsafe-eval` in `scriptSrc`, which further weakens XSS protection.

## Code Quality Findings

### CQ1. Silent Error Swallowing (40+ instances) — HIGH
**Key files:**
- `backend/src/routes/demo-seed.ts` — 9 empty `catch (e) {}` blocks (lines 769-797, 1044-1062)
- `backend/src/services/evidence/EvidenceVaultService.ts` — 7 fire-and-forget `.catch(() => {})` patterns

- `backend/src/middleware/cacheMiddleware.ts:84,134`
- `backend/src/services/gateway/SIEMIntegration.ts:149,155,409`

**Impact:** Failed operations (cache writes, data deletions, SIEM forwarding) go undetected. At minimum, add `logger.warn()` to all catch blocks.

### CQ2. Excessive `as any` Type Assertions (75+ instances) — HIGH
**Worst files:**
- `backend/src/routes/aegis.ts` — 11 instances
- `backend/src/services/evidence/TestEvidenceLedgerService.ts` — 3 instances
- `backend/src/security/DefenseInDepth.ts` — 3 instances

### CQ3. Type-Erased Classes — MEDIUM
**File:** `backend/src/services/CendiaDissentService.ts:28-30`
```typescript
export class Dissent { [key: string]: any; }
export class DissenterProfile { [key: string]: any; }
```
These classes are untyped bags — they defeat TypeScript's purpose entirely.

### CQ4. Service Proxy Silently Returns Null — MEDIUM
**File:** `backend/src/services/_serviceProxy.ts`

The `withFallback` wrapper silently returns `null` for unimplemented methods. 34 services use this pattern, meaning unimplemented features return null instead of proper 501 errors.

### CQ5. Missing Database Indexes — MEDIUM
- 116 `@@unique` constraints across schema files but only 571 total indexes
- Several foreign key columns (e.g., `audit_logs.user_id`) lack single-column indexes
- No temporal indexes on `created_at` for time-range queries

### CQ6. Disabled TypeScript Strictness — MEDIUM
**Frontend `tsconfig.json`:** `noUnusedLocals: false`, `noUnusedParameters: false`, `noUncheckedIndexedAccess: false`
**Backend `tsconfig.json`:** `noUnusedLocals: false`, `noUnusedParameters: false`, `noImplicitReturns: false`

These disabled checks allow dead code and unsafe property access to accumulate.

### CQ7. Dynamic Route Loading Without Error Boundaries — LOW
**File:** `backend/src/index.ts:308-312, 374-376, 391-394`

Three routes use `import().then().catch(() => {})` — if these modules fail to load, no error is logged and no 503 is returned. Only a silent empty catch.
